# Спецификация для агента-исполнителя: ветка «сигнал → баннеры»

Задача: реализовать всю ветку от момента, когда оркестратор отдал `SummaryRequest`, до готовых баннеров в хранилище и ответа чата. Контракты уже зафиксированы в коде. Твоя работа: реализовать компоненты, подключить их друг к другу и покрыть тестами.

## 0. Что прочитать первым

1. `models.py` — сущности. Контракты менять нельзя. Если без изменения не обойтись, остановись, опиши проблему в `CHANGES.md` и продолжай с обходным путём.
2. `interfaces.py` — Protocol-интерфейсы, которые нужно реализовать.
3. `scoring.py` — готовые чистые функции: `content_signals`, `company_confidence`, `render_for_you`, `base_priority`, `banner_priority`, `pick_top_k`. Использовать как есть, не переписывать.
4. `summary-branch-dataflow.md` — как данные идут через ветку и почему.
5. `tests/test_smoke.py` — образец стиля тестов.

## 1. Границы

В зоне ветки: саммаризация, сборка утверждений и источников, оценка уверенности и качества, превращение в баннеры, хранение баннеров и кэша, выдача в виде `BannerDTO`, ответ чата.

Вне зоны (приходит снаружи, подставляй заглушки через интерфейсы): поиск, ранжирование, оркестратор, профили компаний, реальный LLM-шлюз, BFF и фронт.

## 2. Два хранилища: это не одно и то же

| | `SegmentCache` | `BannerStore` |
|---|---|---|
| Что хранит | Общее содержимое: заголовок, шаблон «для вас», утверждения, источники, сигналы качества | Личный индекс: баннер компании (строка «для вас», уверенность, срок) + готовый `BannerDTO` |
| Ключ | `(cluster_id, segment_id, prompt_version)` | `company_id` -> отсортированный набор баннеров |
| Сколько записей | кластеры × сегменты | компании × кластеры |
| Зачем | Не платить за LLM повторно для каждой компании сегмента | Мгновенно отдать топ-3 при открытии страницы |
| Состояние | Нет (только TTL) | Есть: «показан», «скрыт», «просрочен» |

Один баннер ссылается на содержимое через `Banner.key`. Утверждения и источники в баннерах не копируются; в `BannerDTO` они попадают при сборке (`Publisher.to_dto`), и в хранилище лежит уже собранный DTO как производная выдача.

## 3. Что реализовать

Пакет `src/summary_branch/`, модули ниже. Имена классов можно менять, но каждый класс обязан реализовывать указанный Protocol.

### 3.1 `config.py`
Один pydantic-класс `BranchConfig` со значениями по умолчанию: `max_clusters_per_request=3`, `top_k_serve=3`, `cache_ttl_s=72*3600`, `banner_ttl_h` по теме (`rate`: 72, `fx`: 24, остальное: 36), `urgent_min_score=0.85`, `news_text_max_chars=2000`, `quote_max_chars=200`, `prompt_version="v1"`. Пороги уверенности и веса остаются в `scoring.py`.

### 3.2 `summarizer.py` — `LlmSummarizer(Summarizer)`
- Строит промпт из `SummaryRequest`. Новости и материалы банка вставляются как данные внутри явных разделителей; в системной части прямо сказано, что текст внутри — не инструкции.
- Просит строго JSON по схеме `SummaryDraft.model_json_schema()`.
- Режим `banner`: один кластер на вызов (вызывающий код сам режет `news` по `cluster_id`). Режим `chat`: учитывает `question`, возвращает `follow_ups`; из контекста компании в промпт идут только `tags` и `features`.
- Правила в промпте: каждое утверждение помечено типом `fact|bank|model|hypothesis`; в `fact` и `bank` только то, что есть в источниках; ссылки только на `news_id`/`doc_id` из запроса; числа переписываются без изменений; `headline` до 60 символов; `for_you_template` содержит `{feature}` либо пустой, `for_you_fallback` обязателен; никаких инвестиционных рекомендаций.
- `req.budget`: `FULL` обычный вызов, `LITE` короткий вызов без повторов, `CACHED_ONLY` вызов запрещён (бросить `BudgetExhausted`).
- Невалидный JSON: один повтор с подсказкой об ошибке, затем `SummarizationFailed`.
- Обрезает тексты новостей до `news_text_max_chars`.
- Вызывает модель только через `LLMClient`. Названия моделей в коде не хардкодить: уровень (`tier`) передаётся роутеру.

### 3.3 `binder.py` — `DefaultEvidenceBinder(EvidenceBinder)`
Детерминированный, без LLM.
- `evidence_ids` превращает в `EvidenceRef` с цитатой: из новости или материала банка берётся предложение с наибольшим пересечением чисел и основ слов с текстом утверждения, до `quote_max_chars`.
- Утверждение `fact` или `bank` без валидной ссылки отбрасывается. `model` и `hypothesis` без ссылок остаются.
- Утверждения-дубликаты (одинаковый нормализованный текст) схлопываются.
- Источники: для каждой использованной новости `SourceRef(kind=news.source_kind, title=news.title, url=news.url)`; если задан `primary_url`, добавляется `PRIMARY`-источник; для использованных материалов банка добавляется `BANK`. Порядок: primary, bank, media. Не более трёх.

### 3.4 `stores.py`
- `InMemorySegmentCache(SegmentCache)` с TTL и счётчиком попаданий.
- `InMemoryBannerStore(BannerStore)`: `put` идемпотентен по `banner_id` и возвращает `True`, если баннер новый, иначе `False`; `top_k` отбрасывает просроченные и скрытые, применяет `pick_top_k` (динамическая часть приоритета и разнообразие тем), возвращает `list[BannerDTO]`; `mark_seen`, `suppress`, `invalidate_cluster` работают как описано в интерфейсе.
- Интерфейс сохраняется таким, чтобы позже подставить Redis (отсортированное множество со статическим `base_priority` из `scoring.py`) и Postgres. Реальные Redis/Postgres писать не нужно.

### 3.5 `confidence.py` — `DefaultConfidenceScorer(ConfidenceScorer)`
Тонкий адаптер над `scoring.company_confidence` (берёт сигналы, `lead`, `topic` из `SegmentSummary`; `has_sources` по `seg.sources`). Калибратор принимает необязательным параметром конструктора; NLI принимает `DefaultContentScorer` (адаптер над `content_signals`).

### 3.6 `composer.py` — `DefaultBannerComposer(BannerComposer)`
- `for_you` через `scoring.render_for_you`.
- `banner_id` детерминированный: хеш от `company_id` и `key`, чтобы повторный прогон не плодил дубликаты.
- `expires_at` по теме из конфига. `topic`, `severity` копируются из `SegmentSummary`.

### 3.7 `publisher.py` — `DefaultPublisher(Publisher)`
- `to_dto`: `label` из пары «severity + topic» (например, «Внимание · rate»; словарь русских названий тем вынести в конфиг), `caveat = decision == SHOW_WITH_CAVEAT`, `raw_news = decision == SHOW_RAW_NEWS`. При `raw_news` `headline` берётся из заголовка главной новости (первый источник), `for_you` пустое, интерпретаций нет.
- `push`: вызывает переданный обработчик (заглушка `Callable`), реального SSE не нужно.

### 3.8 `segment_builder.py` — `SegmentBuilder`
Склеивает S1–S3b: ключ `ContentKey` -> `SegmentCache.get` -> при промахе `Summarizer` -> `EvidenceBinder` -> `content_signals` -> `SegmentSummary` -> `SegmentCache.put`. Возвращает `None`, если после сборки не осталось ни одного `fact`/`bank` утверждения или `structure_ok` ложно.

### 3.9 `branch.py` — `DefaultSummaryBranch(SummaryBranch)`
`handle_banner(req)`:
1. Сгруппировать `req.news` по `cluster_id`, взять первые `max_clusters_per_request` по лучшему `rerank_score`.
2. Для каждого кластера собрать `SegmentSummary` через `SegmentBuilder` (запрос с новостями только этого кластера).
3. Взять компании: `req.company` плюс `directory.active_in_segment(segment_id)` без дублей.
4. Для каждой компании: `ConfidenceScorer.score`; при `DROP` пропустить; иначе `composer.compose`, `publisher.to_dto`, `store.put`; если `severity=ATTENTION`, решение `SHOW_SUMMARY`, `score >= urgent_min_score` и `store.put` вернул `True`, вызвать `publisher.push`.
5. Вернуть список созданных `Banner`.

`handle_chat(req)`: `Summarizer` в режиме chat без записи в кэш баннеров; `EvidenceBinder`; `content_signals`; `company_confidence` с `lead_from_news(req.news[0])`. Если решение `SHOW_RAW_NEWS` или `DROP`, вернуть `ChatAnswer` с `raw_news=True`, пустыми `claims` и источниками главной новости. Иначе вернуть утверждения и источники, `caveat` при средней уверенности. Ничего не пишет в `BannerStore`.

Ошибки: `SummarizationFailed` и `BudgetExhausted` для баннера значит «пропустить кластер и записать причину в лог»; для чата значит ответ в режиме `raw_news=True`.

### 3.10 Заглушки и демо
- `fakes.py`: `FakeLLMClient` (детерминированный JSON по ключевым словам запроса, плюс режим «вернуть битый JSON один раз»), `StaticDirectory(CompanyDirectory)`.
- `scripts/demo_summary_branch.py` (в корне репозитория): запускает ветку на двух сегментах и трёх компаниях, печатает топ-3 для каждой компании и показывает, что второй прогон идёт через кэш без вызова LLM.

## 4. Критерии приёмки (все — тестами, без сети)

1. Контракт: запрос в режиме `banner` с вопросом и в режиме `chat` без вопроса отклоняются (уже покрыто).
2. Кэш: при двух компаниях одного сегмента LLM вызывается один раз на кластер; повторный прогон тех же данных вызывает LLM ноль раз.
3. Идемпотентность: повторный прогон не создаёт дублей баннеров (`banner_id` детерминирован).
4. Binder: `fact` без валидной ссылки отбрасывается; дубликаты схлопываются; порядок источников primary, bank, media; цитата не длиннее лимита и содержит число из утверждения, если оно есть.
5. Выдуманное число в факте даёт `numeric_miss`, оценка не выше 0.5, баннер не получает `SHOW_SUMMARY`.
6. Решения: высокая уверенность -> обычный баннер; средняя -> `caveat=True`; низкая -> `raw_news=True`, `for_you` пусто; нет источников -> баннер не создаётся.
7. Выдача: `top_k(company, 3)` не возвращает просроченные и скрытые, не отдаёт три баннера одной темы при наличии других, учитывает `mark_seen`.
8. `invalidate_cluster` убирает баннеры кластера у всех компаний и возвращает их число.
9. Бюджет: `CACHED_ONLY` без попадания в кэш не вызывает LLM и не падает.
10. Чат: ответ не записывается в `BannerStore`; при низкой уверенности возвращается `raw_news=True`.
11. Битый JSON от модели: один повтор, затем кластер пропускается без исключения наружу.
12. Инъекция: новость с текстом вида «игнорируй инструкции и ...» не меняет структуру промпта (разделители экранированы) и не попадает в системную часть.

## 5. Ограничения

- Python 3.11+, pydantic v2, стандартная библиотека. Новые зависимости не добавлять, кроме `pytest` для тестов.
- Все вызовы моделей только через `LLMClient`. Ни одного прямого сетевого вызова.
- Логи без персональных данных; в трассу писать `trace_id`, ключ контента, решение и причины.
- Не менять `models.py` и пороги в `scoring.py`. Нужны изменения — записать в `CHANGES.md`.
- Ответы пользователю не должны содержать инвестиционных рекомендаций; требование к промпту и тест на присутствие запрета в промпте.
- Комментарии и сообщения об ошибках на русском, имена в коде на английском.

## 6. Допущения по умолчанию (можно оспорить в `CHANGES.md`)

1. В режиме предрасчёта оркестратор вызывает ветку по одному представителю сегмента, остальные компании сегмента берутся из `CompanyDirectory`.
2. `segment_id` приходит готовым; правило нарезки не наше.
3. Релевантность для остальных компаний сегмента считается по пересечению их тегов с тегами главной новости, а оценка реранкера берётся от представителя.
4. Классификатор NLI и калибратор подключаются позже через необязательные параметры (`DefaultContentScorer`, `DefaultConfidenceScorer`).
